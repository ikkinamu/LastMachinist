이 문서는 Last Machinist 전체 게임의 최종 명세가 아니다.

Master Spec v0.2에 정의된 전체 방향 중,
게임의 핵심 재미를 검증하기 위해 실제로 구현할 최소 수직 슬라이스(Vertical Slice)를 정의한다.

MVP의 질문은 하나다.

"고장난 부품을 관찰하고, 직접 측정하고, 원래 형상을 추론하고,
직접 가공해서 실제 시설을 다시 움직이게 만드는 과정이 재미있는가?"

MVP는 이 질문을 검증하는 데 필요하지 않은 기능을 의도적으로 제외한다.

MVP 종료 조건:
QUEST 01 「멈춰버린 펌프」를 처음부터 끝까지 플레이할 수 있고,
플레이어가 직접 제작한 축을 설치하여 펌프가 다시 작동하는 장면까지 확인할 수 있다.

0.1 v0.8 우선순위 및 통합 규칙
============================================================

이 문서는 MVP Development Spec v0.3의 전체 내용을 계승하고,
다음 두 상세 명세를 본문에 정식 통합한 단일 구현 기준 문서다.

- Measurement System Implementation Spec v1.0
- Presentation / Environment / Scene Composition Spec v1.0

따라서 Codex에 MVP를 구현/수정시킬 때 별도 문서 간 우선순위를 추측하게 하지 않는다.
이 v0.8 파일 하나를 MVP의 현재 Source of Truth로 사용한다.

충돌 시 우선순위:

1. Section 97~103의 v0.8 신규/수정 규칙
2. Section 89~95의 v0.7 신규/수정 규칙
3. Section 78~88의 v0.6 신규/수정 규칙
4. Section 64~77의 v0.5 신규/수정 규칙
5. Section 60 측정 시스템 상세 구현 명세
6. Section 61 화면 연출·환경·씬 구성 상세 구현 명세
7. Section 48 가공 카메라 시스템 및 Section 61.6 Projection Requirements
8. Section 40 이후의 상세 재정의
9. 그보다 앞선 기존 MVP 설명

즉, 앞부분의 요약/예전 구현 설명이 최신 상세 규칙과 충돌하면 최신 상세 규칙이 절대 우선한다.

특히 다음 항목은 절대 규칙이다.
- Player-Facing 기본 언어 = 한국어
- 측정은 숫자 결과창이 아니라 실제 눈금 직접 판독형
- TrueDimension / InstrumentReading / RecordedMeasurement 완전 분리
- MeasurementPoint = 어디를 측정하는지 정의하는 지점
- WorkMemo = 플레이어가 확보한 정보만 점진적으로 해금
- DialoguePage = 화면 하단 약 30~35% 고정
- QuestPopup / QuestTracker / QuestLogPage 역할 분리
- 가공/측정 핵심 화면을 대형 Quest UI가 가리면 안 됨
- Workshop/Farm/Pump를 빈 Primitive 수준으로 완료 처리하지 않음
- Pump는 QUEST 01의 Hero Prop으로 식별 가능한 형태와 복구 전후 변화가 필요
- 가공 Camera Projection 자체가 Orthographic이어야 함
- Perspective Camera를 단순히 정면/평면 방향으로 돌린 것을 직교 View로 인정하지 않음
- 정면/평면/우측면/등각투영 4개의 고정 View 사용
- 자유 Orbit Camera 및 가공 중 Mouse Wheel Zoom 금지
- Quest State별 허용/금지 행동을 실제 시스템에서 강제

0.2 v0.7 통합 문서 사용법
============================================================

Codex는 이 파일을 처음부터 끝까지 기준 문서로 취급한다.
하지만 실제 수정 작업은 기능/페이지/씬 단위로 나누어 수행한다.

권장 방식:
- 전체 문서 = 변경 불가 기준/계약
- 이번 작업 지시 = 수정할 Page 또는 System 범위
- 구현 전 = 현재 프로젝트 Audit
- 구현 후 = 해당 Section의 PASS/FAIL 검증

Codex가 문서가 길다는 이유로 최신 상세 Section을 생략하거나
자의적으로 더 단순한 UI/측정/환경 구현으로 대체하면 안 된다.

6. 아키텍처 원칙
============================================================

1. Game State와 UI를 분리한다.
2. Workpiece 계산 데이터와 화면 Mesh를 분리한다.
3. Quest 진행 로직을 NPC MonoBehaviour 내부에 직접 하드코딩하지 않는다.
4. Item 정의와 Item 보유 상태를 구분한다.
5. Measurement의 실제값/기기표시값/플레이어기록값을 구분한다.
6. 저장 가능한 데이터에 Unity Scene Object 직접 참조를 넣지 않는다.
7. ScriptableObject는 정적 정의 데이터에 사용한다.
8. 런타임 상태는 직렬화 가능한 순수 C# 데이터 중심으로 관리한다.
9. Turning은 첫 공정일 뿐이므로 Workpiece/Quest/Save가 Turning 전용이 되지 않게 한다.
10. MVP에 필요하지 않은 거대한 범용 프레임워크는 만들지 않는다.

8. Turning Geometry — Round Profile
============================================================

MVP의 선삭 공작물은 Z축 방향의 반경 프로파일로 계산한다.

개념:

Z 위치별 현재 Radius를 저장하거나,
구간(segment) 기반 프로파일을 저장한다.

권장 MVP 방식:
구간 기반 + 필요 시 샘플링.

TurningProfile:
- TotalLength
- Segments[]

TurningSegment:
- StartZ
- EndZ
- Radius

표시 직경:
Diameter = Radius × 2

중요:
내부 계산은 Radius를 사용할 수 있으나,
플레이어 UI는 기계가공 도면/측정 맥락에 맞게 Diameter를 표시한다.

가공:
공구가 특정 Z 범위를 지나며 현재 Radius보다 안쪽으로 진입하면
해당 영역의 Radius가 감소한다.

절대 금지:
- 재료를 다시 붙이는 것
- 과가공 후 Undo 없이 원래 치수로 자동 복원

Undo는 개발/디버그 기능으로만 둘 수 있으며 정식 플레이에는 제공하지 않는다.


============================================================
9. Visual Mesh
============================================================

TurningProfile을 기반으로 회전체 Mesh를 생성한다.

목표:
- 프로파일 변경 시 화면 형상 갱신
- 지나치게 높은 폴리곤 불필요
- 계산 정확도와 렌더링 세그먼트 수 분리

필요 기능:
- 원형봉 렌더링
- 단차 표현
- 모따기 표현
- 회전 애니메이션
- 가공 중 단순 칩/효과 가능

MVP에서는 실제 물리 절삭 시뮬레이션을 구현하지 않는다.

10. 선반 상태 머신
============================================================

LatheController는 최소한 다음 상태를 관리한다.

Idle
Setup
Ready
SpindleRunning
Machining
Measuring
Reclamping
Finished

예:

Idle
→ Workpiece 장착
→ Setup
→ Tool 장착
→ Ready
→ Spindle ON
→ SpindleRunning
→ Tool 접촉
→ Machining

측정:
SpindleRunning 상태에서는 정밀 측정을 허용하지 않는다.

재고정:
주축 정지
→ Reclamping
→ Workpiece 방향 반전
→ 기준 좌표 갱신
→ Ready


============================================================
11. MVP 선반 입력 시스템 — 확정
============================================================

핵심 철학:

- 키보드 = 상태/기능 선택용 빠른 입력
- 마우스 휠 = 선택된 축 핸들을 돌리는 빠른 PC 입력
- 화면 UI = 마우스로 직접 조작 가능한 실제 게임 조작반
- 추후 모바일 = 동일한 화면 UI를 터치로 조작

즉, 키보드/마우스/UI/터치는 서로 다른 게임 로직을 호출하지 않는다.
모든 입력은 동일한 Lathe Command 계층으로 들어간다.

예:

Keyboard
Mouse Wheel
UI Button / UI Dial
Future Touch
        ↓
LatheInputRouter
        ↓
Lathe Commands
        ↓
LatheController / Domain Logic


[11.1 축 선택]

PC 단축 입력:
- X 키 → X축 선택
- Z 키 → Z축 선택

마우스 휠은 현재 선택된 축을 이동시킨다.

예:
SelectAxis(Axis.X)
SelectAxis(Axis.Z)

화면에는 현재 선택 축을 항상 표시한다.

예:
AXIS: X
또는
AXIS: Z


[11.2 이동 배율]

세 단계 배율:

- ×100
- ×10
- ×1

키보드 예시:
- 1 → ×1
- 2 → ×10
- 3 → ×100

키 배치는 추후 변경 가능하며 Input System에서 리바인딩 가능하게 설계한다.

중요:
×100 / ×10 / ×1은 현실 공작기계의 특정 이송량을 그대로 의미하지 않는다.
게임 조작용 상대 배율이다.

내부 값 예:
Fine
Medium
Coarse

실제 이동량은 플레이테스트로 결정한다.


[11.3 마우스 휠 입력]

마우스 휠:
- 현재 선택된 축의 Handwheel 입력
- 휠 방향에 따라 + / - 이동

예:

Mouse Wheel Delta
× CurrentMovementScale
→ ApplyHandwheelDelta(CurrentAxis, delta)

휠 한 칸의 실제 이동량은 게임 밸런스 값으로 관리한다.

중요:
마우스 휠은 공구 좌표를 직접 설정하지 않는다.
반드시 Handwheel Command를 통해 이동한다.


[11.4 화면 다이얼 직접 조작]

화면에 X축 핸들과 Z축 핸들을 별도로 표시할 수 있다.

- X 핸들을 마우스로 잡아 돌리면 X축 이동
- Z 핸들을 마우스로 잡아 돌리면 Z축 이동

직접 다이얼을 조작할 때는 별도의 "현재 선택 축"이 필요하지 않다.
잡은 핸들의 축을 직접 사용한다.

회전 계산 개념:

Pointer Position
→ Dial Center 기준 atan2
→ 이전 각도와 현재 각도 차이
→ Delta Angle
→ Handwheel Delta
→ 해당 축 이동

각도는 -180/180 경계에서 튀지 않도록 DeltaAngle 방식으로 처리한다.

다이얼 회전은 화면의 시각적 회전과 실제 이동량을 같은 Command로 연결한다.


[11.5 모바일 확장]

모바일에서는:
- 키보드 단축키 없음
- 마우스 휠 없음
- 동일 UI 버튼/다이얼을 터치로 조작

따라서 MVP부터 모든 핵심 기능은 반드시 화면 UI로도 실행 가능해야 한다.

키보드는 필수 기능의 유일한 접근 방식이 되어서는 안 된다.


[11.6 주축]

주축 기능:
- 회전 시작
- 정지

PC:
- 단축키 제공

UI:
- 화면 버튼 제공

둘 다 동일 Command 사용.

예:
SetSpindleRunning(true)
SetSpindleRunning(false)

MVP에서는 정/역회전의 복잡한 활용이 필요하지 않다면 한 방향 회전만 구현 가능하다.
역회전은 향후 실제 게임 필요가 생겼을 때 확장한다.


[11.7 공구 / 측정 / 재고정]

다음 기능 역시:
- 키보드 단축키
- 화면 UI
둘 다 제공할 수 있어야 한다.

- 공구 선택
- 측정 모드 진입
- 재고정
- 작업 종료

단축키와 UI는 모두 같은 Command를 호출한다.


[11.8 현재 상태 HUD]

최소 표시:

AXIS      X / Z
SCALE     ×1 / ×10 / ×100
SPINDLE   ON / OFF
TOOL      현재 공구
MODE      Machining / Measuring / Reclamping 등

초기 낡은 선반에서는 공구의 절대 X/Z 좌표를 고정밀 숫자로 계속 노출하지 않는다.

이유:
실시간 고정밀 좌표 표시가 있으면 버니어 측정 시스템의 필요성이 약해진다.

향후 위치 표시 장치(DRO 등)를 복구/장착하는 progression으로 확장 가능하다.


[11.9 입력 충돌 방지]

마우스 휠은 UI ScrollView, 카메라 Zoom 등과 충돌할 수 있다.

따라서 Lathe Mode에서는 Input Context를 명확히 분리한다.

예:

GameplayContext
DialogueContext
LatheContext
MeasurementContext
UIContext

LatheContext에서:
- 마우스 휠 = Handwheel

MeasurementContext에서:
- 마우스 휠 = 측정기 조작 등에 사용 가능

일반 UI Scroll 영역 위에서는 Handwheel 입력을 차단할 수 있다.

카메라 Zoom에 마우스 휠을 동시에 사용하지 않는다.


[11.10 Input Architecture]

권장 클래스:

LatheInputRouter
- 키보드
- 마우스 휠
- UI
에서 들어온 입력을 Lathe Command로 변환

LatheCommandService 또는 LatheController 공개 Command:
- SelectAxis(Axis axis)
- SetMovementScale(MovementScale scale)
- ApplyHandwheelDelta(Axis axis, float delta)
- SetSpindleRunning(bool running)
- SelectTool(string toolId)
- EnterMeasurementMode()
- RequestReclamp()
- FinishMachining()

UI 버튼이 LatheController 내부 상태를 직접 변경하지 않는다.
반드시 Command 계층을 사용한다.


[11.11 실제 절삭 발생 조건]

공구 이동 = 항상 절삭이 아니다.

절삭은 최소 다음 조건이 만족될 때만 발생한다.

- Workpiece 장착
- SpindleRunning
- 절삭 가능한 Tool 장착
- Tool과 Workpiece Geometry 접촉
- 현재 Lathe State가 Machining 가능 상태

그 외 이동은 단순 위치 이동이다.

이를 통해:
- 주축 정지 상태에서 공구 위치 조정
- 측정 준비
- 재고정 전 이동
등을 구분한다.


[11.12 X축 내부값과 UI 의미]

Turning 계산은 Radius 기반으로 구현할 수 있다.

그러나 플레이어에게 익숙한 가공/측정 정보는 Diameter 기준으로 제시한다.

따라서:

Internal X Geometry = Radius
Displayed Diameter = Radius × 2

입력 핸들의 실제 내부 이동량과
화면에 표시되는 치수 의미를 혼동하지 않도록 변환 책임을 한 곳에 둔다.

예:
TurningCoordinateConverter

MVP에서 정밀 DRO는 표시하지 않더라도
평가/측정 시스템은 이 규칙을 일관되게 사용한다.


[11.13 재고정과 입력 좌표]

공작물을 뒤집어도 플레이어의 X/Z 조작 방향이 갑자기 뒤집힌 것처럼 느껴지지 않아야 한다.

Workpiece Orientation:
- Normal
- Reversed

재고정 시 Geometry 데이터 자체를 무작정 역순으로 파괴적으로 변환하기보다,
Workpiece Local Coordinate ↔ Machine Coordinate 변환 계층을 둔다.

Lathe Input은 Machine Coordinate 기준으로 일관되게 처리하고,
Geometry 접근 시 Orientation을 반영한다.


[11.14 입력 피드백]

마우스 휠 또는 다이얼 조작 시:
- 해당 핸들 시각적 회전
- 작은 클릭/기계음
- 선택 축 강조
- 이동량에 따른 시각 피드백

×100:
큰 이동 감각

×10:
중간 이동 감각

×1:
미세 이동 감각

배율 차이는 수치뿐 아니라 체감에서도 느껴져야 한다.

12. MVP 공구
============================================================

최소 구현 공구:

1. 황삭 바이트
2. 모따기 바이트

선택적으로 디버그용 공구를 별도 제공할 수 있으나 게임 데이터에는 노출하지 않는다.

ToolDefinition:
- Id
- DisplayName
- ToolType
- RemovalCapability
- BasePrecision
- CanChamfer
- Description

MVP에서는 복잡한 공구 수명/날끝 형상 계산은 제외한다.

다만 향후 ToolCondition을 붙일 수 있도록 Tool Instance 구조는 확장 가능하게 둔다.


============================================================
13. 공작물 재고정
============================================================

QUEST 01의 핵심 가공 경험 중 하나.

목표 축은 중앙 Ø50을 남기고 양쪽 Ø40을 만드는 대칭 구조다.

플레이어는 한 방향에서 접근 가능한 부분을 가공한 뒤,
공작물을 방향 전환하여 다시 고정할 수 있다.

Reclamp 동작:
- 주축 정지 확인
- 현재 Workpiece 분리
- 프로파일 방향 반전 또는 좌표 Transform 적용
- 기준점 재설정
- 다시 장착

데이터 자체를 파괴적으로 뒤집기보다,
Workpiece orientation을 관리하는 방식을 우선 고려한다.

예:
Orientation = Normal / Reversed

UI와 공구 좌표 변환에서 Orientation을 반영한다.


============================================================
14. 모따기
============================================================

MVP에서는 모따기를 정교한 CAD Feature 시스템으로 과도하게 만들지 않는다.

필요:
- 모따기 바이트 선택
- 지정 가장자리에 간단한 Chamfer 생성
- 프로파일에 경사 구간 반영
- 최종 형상 판정에서 존재 여부 확인 가능

ChamferFeature:
- Position
- Width
- Angle(optional)
- IsValid

첫 펌프 축의 모따기 요구는 관대하게 설정한다.


============================================================
15. 측정 시스템 핵심
============================================================

절대 합치지 말 것:

TrueDimension
InstrumentReading
RecordedMeasurement

TrueDimension:
현재 Workpiece Geometry에서 계산되는 실제 게임 내부 치수.

InstrumentReading:
측정기 특성이 반영되어 측정기 화면/눈금에 나타날 값.

RecordedMeasurement:
플레이어가 눈금을 보고 직접 입력한 값.

MVP에서는 복잡한 측정 오차 모델을 생략할 수 있다.

단:
플레이어가 틀리게 읽어도 RecordedMeasurement를 자동 수정하지 않는다.

낡은 버니어 캘리퍼스

획득:

18. Measurement Point
============================================================

19. 고장 펌프 축 데이터
============================================================

정상 설계값:

TotalLength = 100 mm

L1:
Length = 30 mm
Diameter = 40 mm

L2:
Length = 40 mm
Diameter = 50 mm

L3:
Length = 30 mm
Diameter = 40 mm

형상:
좌우대칭 3단 축.

고장품:
- L1 정상에 가까움
- L2 정상에 가까움
- L3 직경 마모
- L3 끝/길이 방향 마모

중요:

플레이어는 CurrentGeometry를 측정하여 TargetGeometry를 추론해야 한다.

L3 마모 수치는 밸런스/시각화 단계에서 확정한다.
현재 문서에서는 임의의 마모 수치를 하드코딩하지 않는다.

20. Target Part / 평가 데이터
============================================================

PartRequirement:
- Id
- RequiredGeometry
- FunctionalTolerance
- RequiredFeatures
- OptionalFeatures

PumpShaftRequirement:

RequiredGeometry:
- 30 mm 구간 Ø40
- 40 mm 구간 Ø50
- 30 mm 구간 Ø40
- 전체 100 mm

RequiredFeatures:

- 필요한 가장자리 모따기

MVP에서는 기하공차/표면거칠기 없음.

FunctionalTolerance:
첫 퀘스트는 넓게 설정하되 구체 수치는 플레이테스트에서 결정한다.

판정 결과:
Perfect
Acceptable
Reworkable
Rejected

Perfect:
목표 형상에 매우 가까움.

Acceptable:
정밀하지 않아도 펌프에 장착되어 기능 가능.

Reworkable:
재료가 아직 남아 있어 추가 가공으로 수정 가능.

Rejected:
과가공 등으로 현재 공작물을 복구할 수 없음.

35. Codex 작업 규칙
============================================================

Codex에게 매 Phase마다 다음을 요구한다.

1. 기존 파일을 먼저 읽고 현재 구조를 파악할 것.
2. 기존 공개 API를 불필요하게 깨지 말 것.
3. 변경 파일 목록을 먼저 계획할 것.
4. 구현 후 컴파일 오류 가능성을 자체 검토할 것.
5. 신규 클래스 책임을 한 문장으로 설명할 수 있어야 한다.
6. MonoBehaviour에 데이터/도메인 로직을 과도하게 몰아넣지 말 것.
7. Inspector에서 설정할 값과 런타임 값을 명확히 구분할 것.
8. 문자열 ID를 여기저기 직접 입력하지 말고 중앙 정의/데이터를 사용할 것.
9. 테스트 가능한 순수 C# 로직은 MonoBehaviour에서 분리할 것.
10. TODO로 핵심 기능을 비워둔 채 완료했다고 하지 말 것.
11. Placeholder가 필요한 경우 명확히 표시할 것.
12. 범위를 넘어 Master Spec의 후반 시스템을 임의로 구현하지 말 것.

36. MVP 성공 기준
============================================================

기술적 성공:

- Unity에서 오류 없이 실행된다.
- QUEST 01을 처음부터 끝까지 진행할 수 있다.
- 선반에서 실제 Workpiece Geometry가 변경된다.
- 공작물 재고정 후 반대쪽 가공이 가능하다.
- 버니어 눈금을 직접 읽을 수 있다.
- 플레이어 입력 측정값이 별도로 기록된다.
- 완성품이 실제 Geometry 기준으로 평가된다.
- 소재 실패/재시도가 가능하다.
- Save/Load가 핵심 상태를 보존한다.
- 펌프가 실제로 복구 상태로 변한다.

게임적 성공:

플레이어가 다음 흐름을 이해한다.

"왜 이 부품이 필요한가"
→ "어디가 망가졌는가"
→ "원래 어떻게 생겼는가"
→ "어떻게 만들어야 하는가"
→ "내가 제대로 만들었는가"
→ "내가 만든 것이 어디에 쓰였는가"

그리고 마지막에:

"내가 깎은 축 때문에 펌프가 다시 돌아갔다."

라는 인과관계를 명확하게 느낄 수 있어야 한다.

============================================================
38. 구현 시 절대 지킬 MVP 원칙
============================================================

1. MVP 종료점은 첫 펌프 복구다.
2. MVP에 3D 탐색을 넣지 않는다.
3. 첫 소재는 외삼촌이 남긴 탄소강 원형봉 3개다.
4. 첫 정밀 측정기는 박성철에게 받는 낡은 버니어다.
5. 버니어는 숫자를 자동 표시하지 않는다.
6. 고장 축에 정식 도면을 제공하지 않는다.
7. L3 마모를 통해 플레이어가 원형을 추론하게 한다.
8. 정상 축은 100 mm / Ø40×30 / Ø50×40 / Ø40×30이다.
9. 첫 의뢰는 엄격한 정밀가공 시험으로 만들지 않는다.
10. 가공 결과는 실제 Geometry로 평가한다.
11. RecordedMeasurement와 실제 Geometry를 혼동하지 않는다.
12. 실패는 가능하지만 MVP가 쉽게 소프트락되지 않게 한다.
13. 제작 성공은 반드시 펌프의 실제 작동으로 보상한다.
14. 후반 시스템을 MVP 코드에 억지로 구현하지 않는다.
15. 동시에 향후 다공정 확장을 막는 하드코딩도 피한다.
16. 실제 위험한 공작기계 조작 훈련기가 아니라 게임용 추상화로 유지한다.

41. 측정 시스템 재정의 — 실제 눈금 판독형
============================================================

[CRITICAL]
측정은 숫자 확인 UI가 아니다.
플레이어가 실제로 버니어 캘리퍼스의 본척/부척 눈금을 보고 값을 읽는 플레이여야 한다.

정상 흐름:

측정 위치 선택
-> Workpiece Geometry에서 TrueDimension 계산
-> 측정기 특성을 거쳐 InstrumentReading 결정
-> 버니어 죠가 해당 치수에 맞게 벌어짐
-> 본척/부척 눈금이 InstrumentReading에 맞게 배치됨
-> 플레이어는 숫자 정답 없이 눈금만 봄
-> 빈 입력칸에 직접 숫자 입력
-> RecordedMeasurement 저장

절대 합치지 말 것:
TrueDimension
InstrumentReading
RecordedMeasurement

TrueDimension:
현재 Workpiece Geometry가 실제로 가진 게임 내부 치수.

InstrumentReading:
현재 측정기에서 플레이어가 읽을 수 있도록 눈금에 반영되는 값.
MVP에서는 고급 오차 모델을 생략하여 TrueDimension과 같을 수 있다.
단, 데이터 구조상 분리한다.

RecordedMeasurement:
플레이어가 눈금을 보고 직접 입력한 값.
잘못 읽어도 그 값을 그대로 저장한다.

예:
TrueDimension = 39.80
InstrumentReading = 39.80
플레이어 입력 = 39.30
RecordedMeasurement = 39.30

이때:
- Workpiece 실제 치수는 39.80 그대로다.
- 39.30으로 Geometry를 수정하지 않는다.
- 즉시 '틀렸습니다'를 표시하지 않는다.
- 정답 39.80을 즉시 공개하지 않는다.

[일반 플레이 UI에서 절대 금지]
- '측정값: 39.80 mm' 자동 표시
- '정답: 39.80 mm' 표시
- 측정 버튼 클릭만으로 입력칸 자동 채움
- RecordedMeasurement 자동 교정
- TrueDimension 디버그 텍스트 상시 노출

TrueDimension과 InstrumentReading은 Editor/Development Debug Panel에서만 직접 확인 가능하다.


============================================================
42. MeasurementPoint 의미 재정의
============================================================

MeasurementPoint는 '정답 숫자를 반환하는 버튼'이 아니다.

MeasurementPoint는:
'버니어를 공작물의 어느 위치에 대는가'를 선택하는 데이터다.

PumpShaftBroken 예:
- L1_Diameter
- L1_Length
- L2_Diameter
- L2_Length
- L3_Diameter
- L3_Length
- TotalLength(optional)

플레이어가 L1_Diameter를 선택하면:
1. 해당 GeometryReference를 찾는다.
2. 현재 고장품 Geometry에서 실제 L1 직경을 계산한다.
3. 결과를 InstrumentReading으로 전달한다.
4. VernierView의 jaw 위치와 본척/부척 눈금을 갱신한다.
5. 숫자 정답은 표시하지 않는다.

MeasurementPoint.DisplayHint는 위치 설명용이다.
예:
'L1 외경'
'중앙 단차 외경'
'마모된 우측 구간 외경'

DisplayHint에 실제 치수 정답을 포함하지 않는다.

43. VernierView 구현 요구
============================================================

VernierView는 장식 이미지가 아니라 InstrumentReading을 시각화하는 기능 UI다.

필수 구성:
- 고정 본척
- 이동 부척
- 측정 죠
- 본척 눈금
- 부척 눈금
- 선택된 측정 위치의 시각적 연결

입력:
- InstrumentReading
- VernierSpecification

출력:
- Jaw opening
- Main scale offset
- Vernier scale offset
- 일치하는 눈금의 실제 시각 정렬

MVP에서 하나의 고정 버니어 사양을 사용한다.
실제 위험한 기계 조작 훈련 수치를 다루지 않는다.
이 시스템은 측정 눈금 읽기 게임플레이만 담당한다.

중요:
눈금 그래픽은 확대했을 때 실제로 읽을 수 있어야 한다.
버니어를 너무 작게 그려 판독이 불가능하면 구현 실패다.

48. 가공 카메라 시스템 — 4개 고정 View
============================================================

가공 화면은 자유 카메라를 사용하지 않는다.
MVP에서는 다음 4개의 고정 Orthographic View를 제공한다.

1. FrontView = 정면
2. TopView = 평면
3. RightView = 우측면
4. IsometricView = 등각투영

[Projection Requirements — 절대 규칙]

이 4개 View는 카메라의 위치/회전만 고정하는 것이 아니다.
Unity Camera의 Projection 자체가 Orthographic이어야 한다.

필수:
- Camera.orthographic = true 또는 동등한 Orthographic Projection 사용
- 화면 깊이에 따른 원근 축소가 없어야 함
- 동일한 크기의 형상은 화면 깊이 차이만으로 더 작거나 크게 보이면 안 됨
- Front / Top / Right / Isometric 모두 Orthographic Projection을 유지
- View 전환은 Orthographic Camera Pose와 Size를 전환하는 방식으로 구현

절대 금지:
- Perspective Camera를 정면으로 돌려놓고 FrontView라고 부르기
- Perspective Camera를 위에서 내려다보게 하고 TopView라고 부르기
- Isometric처럼 보이도록 Perspective FOV만 줄여서 대체하기
- View마다 Orthographic/Perspective가 섞이기

이 규칙의 목적은 공작물의 형상과 단차를 원근 왜곡 없이 읽게 하는 것이다.

Turning 기본 View:
FrontView

향후 Milling 기본 View:
TopView 또는 IsometricView를 공정 데이터에서 지정 가능.

Turning과 향후 Milling은 동일 CameraView 시스템을 공유할 수 있다.
단, MVP에서 Milling 자체는 구현하지 않는다.

필수 조작:
- 키보드 단축키
- 화면 UI 버튼

둘 다 동일 CameraViewCommand를 사용한다.

예:
SetCameraView(CameraView.Front)
SetCameraView(CameraView.Top)
SetCameraView(CameraView.Right)
SetCameraView(CameraView.Isometric)

UI 표시:
[정면] [평면] [우측면] [등각투영]

중요:
- 자유 회전 카메라 없음
- 마우스 드래그로 카메라를 임의 회전하지 않음
- 마우스 휠 Zoom 금지
- 마우스 휠은 LatheContext에서 Handwheel 전용
- View를 바꿔도 LatheControlPanel 위치/사용성이 크게 바뀌지 않음
- 공구와 공작물은 모든 View에서 알아볼 수 있어야 함

미래 모바일:
동일한 4개 UI 버튼을 터치로 사용.

49. WorkMemoPage — 정보 해금형 작업 메모
============================================================

WorkMemoPage는 정답지를 보여주는 화면이 아니다.
플레이어가 실제로 확인한 정보만 기록한다.

초기:

관찰 후:
- 원형 축
- 중앙에 굵은 단차
- 좌우 형상이 비슷해 보임

L1 측정/기록 후:
- L1 외경: 플레이어 기록값
- L1 길이: 플레이어 기록값

L2 측정/기록 후:
- L2 외경: 플레이어 기록값
- L2 길이: 플레이어 기록값

L3 측정 후:
- L3 측정값은 반대쪽과 일치하지 않음
- 마모 상태 표시

중요:
WorkMemo에 자동으로 '정답 Ø40'을 쓰지 않는다.
플레이어가 잘못 읽은 경우 기록값도 잘못될 수 있다.

ShapeInferred 이벤트가 발생한 뒤에는:
'원래 형상 추정' 섹션을 활성화할 수 있다.

최종 추론 예:
- 전체 길이: 100 mm
- 좌측: Ø40 × 30 mm
- 중앙: Ø50 × 40 mm
- 우측: Ø40 × 30 mm
- 우측 구간은 마모되어 현재 측정값을 그대로 원래 치수로 사용하면 안 됨

이 최종 추론은 Quest 로직에서 확정되는 TargetGeometry와 연결되지만,
그 전에는 TargetGeometry를 Player UI에 직접 노출하지 않는다.

추천 플래그:
- ObservedSymmetry
- ObservedL3Wear
- MeasuredL1Diameter
- MeasuredL1Length
- MeasuredL2Diameter
- MeasuredL2Length
- MeasuredL3
- OriginalShapeInferred

60. 측정 시스템 상세 구현 명세 — 통합본
============================================================

[권위 규칙]
이 Section은 MVP의 모든 측정 관련 구현에서 가장 높은 우선순위를 가진다.
앞선 Section의 측정 요약과 충돌하면 Section 60을 따른다.
측정은 Last Machinist의 핵심 게임플레이이며 단순화 대상이 아니다.

============================================================
60.0 이 문서의 목적
============================================================

이 문서는 Last Machinist의 "측정" 시스템을 구현하기 위한 절대 기준이다.

측정 시스템은 단순히 치수를 숫자로 보여주는 기능이 아니다.
측정은 게임의 핵심 플레이 루프 중 하나이며,
플레이어가 실제로 "눈금을 보고, 읽고, 판단하고, 기록하는" 행위 자체가 게임플레이다.

이 문서를 읽고도
"측정 버튼을 누르면 39.80 mm가 뜬다"
같은 구현을 하면 실패다.

가장 중요한 한 문장:

플레이어에게 정답 숫자를 보여주지 않는다.
플레이어는 버니어의 눈금을 직접 보고 값을 읽어야 한다.

============================================================
60.1 측정 시스템의 핵심 철학
============================================================

Last Machinist의 측정은 다음 구조다.

[공작물의 실제 형상]
        ↓
TrueDimension
        ↓
측정기 특성 반영
        ↓
InstrumentReading
        ↓
버니어의 물리적 모양과 눈금 위치로 표현
        ↓
플레이어가 직접 눈금을 읽음
        ↓
직접 숫자 입력
        ↓
RecordedMeasurement

절대로 다음처럼 만들지 않는다.

[공작물 클릭]
→ "39.80 mm"
→ 확인 버튼

이것은 측정 게임이 아니라 숫자 표시창이다.

============================================================
60.2 세 가지 값은 절대 합치지 않는다
============================================================

반드시 아래 3개를 분리한다.

60.1 TrueDimension
60.2 InstrumentReading
60.3 RecordedMeasurement

----------------------------------------
2.1 TrueDimension
----------------------------------------

게임 내부의 실제 공작물 치수.

예:

현재 공작물 실제 지름:
39.80 mm

그러면:

TrueDimension = 39.80

이 값은 Workpiece Geometry에서 계산한다.
플레이어는 이 값을 직접 볼 수 없다.
일반 게임 UI에 절대 표시하지 않는다.

허용:
- Editor
- Development Build Debug Panel
- 자동화 테스트

금지:
- 일반 HUD
- MeasurementPage
- VernierView
- Quest UI
- WorkMemo

----------------------------------------
2.2 InstrumentReading
----------------------------------------

측정기가 실제로 표현해야 할 값.

MVP에서는 복잡한 계측 오차를 생략할 수 있으므로
초기에는 다음처럼 동일할 수 있다.

TrueDimension = 39.80
InstrumentReading = 39.80

하지만 데이터 구조는 반드시 분리한다.

향후:
TrueDimension = 39.80
InstrumentReading = 39.82

같은 시스템을 확장할 수 있어야 한다.

InstrumentReading은 숫자 텍스트로 플레이어에게 보여주는 값이 아니다.
이 값은 버니어의:
- 죠 간격
- 슬라이더 위치
- 본척 위치
- 부척 위치
- 눈금 정렬
을 계산하기 위한 내부 입력값이다.

----------------------------------------
2.3 RecordedMeasurement
----------------------------------------

플레이어가 직접 눈금을 읽고 입력한 값.

예:
TrueDimension = 39.80
InstrumentReading = 39.80

플레이어가 눈금을 잘못 읽음.
플레이어 입력:
39.30

그러면:
RecordedMeasurement = 39.30

게임은 자동으로 다음 행동을 하면 안 된다.
- "틀렸습니다."
- "정답은 39.80입니다."
- 39.30 → 자동으로 39.80 수정

플레이어가 잘못 읽은 기록도 그대로 저장한다.

============================================================
60.3 측정이 실제 플레이에서 어떻게 진행되는가
============================================================

STEP 1. 플레이어가 측정 모드에 들어간다.
STEP 2. 측정할 대상 공작물을 확인한다.
STEP 3. 측정할 위치를 선택한다.
STEP 4. MeasurementPoint가 Workpiece Geometry를 참조하여 실제 치수를 계산한다.
STEP 5. TrueDimension을 얻는다.
STEP 6. 측정기 모델이 InstrumentReading을 생성한다.
STEP 7. 버니어 캘리퍼스가 InstrumentReading에 맞는 위치로 움직인다.
STEP 8. 플레이어 화면에는 버니어 눈금만 보인다.
STEP 9. 플레이어가 눈금을 직접 읽는다.
STEP 10. 플레이어가 빈 입력칸에 직접 숫자를 입력한다.
STEP 11. [기록] 버튼을 누른다.
STEP 12. 입력값을 RecordedMeasurement로 저장한다.
STEP 13. WorkMemo / 검사표 / Quest 진행에 필요한 경우 기록 사실만 전달한다.

중요:
정답 숫자는 STEP 1~13 어디에서도 플레이어에게 자동 공개하지 않는다.

============================================================
60.4 MeasurementPoint의 정확한 의미
============================================================

MeasurementPoint는 "정답 숫자를 반환하는 버튼"이 아니다.
MeasurementPoint는 "플레이어가 측정기를 어느 위치에 대는가"를 정의하는 선택 지점이다.

예:
PumpShaftBroken
- L1_Diameter
- L1_Length
- L2_Diameter
- L2_Length
- L3_Diameter
- L3_Length

L1_Diameter를 선택하면:
60.1 L1 위치를 시각적으로 강조
60.2 해당 위치의 실제 Geometry를 읽음
60.3 현재 지름을 계산
60.4 버니어가 해당 지름만큼 벌어짐
60.5 플레이어가 눈금을 읽음

절대로:
L1_Diameter 선택
→ 40.00 mm 출력

이렇게 만들지 않는다.

============================================================
60.5 버니어 캘리퍼스는 장식 UI가 아니다
============================================================

VernierView는 단순 이미지가 아니다.
측정값에 따라 실제로 움직여야 한다.

필수 구성:
- 고정 죠
- 이동 죠
- 본척(Main Scale)
- 부척(Vernier Scale)
- 슬라이더
- 측정 대상 표시
- 현재 접촉 상태

InstrumentReading이 바뀌면 버니어 모양도 바뀌어야 한다.

예:
InstrumentReading = 37.60
→ 이동 죠가 37.60에 해당하는 위치까지 이동
→ 부척이 본척 위에서 실제 읽을 수 있는 위치에 배치
→ 눈금 정렬이 37.60에 해당해야 함

InstrumentReading = 42.20
→ 이전과 다른 위치로 이동
→ 눈금 정렬도 바뀜

============================================================
60.6 버니어 눈금 구현 원칙
============================================================

MVP에서는 하나의 버니어 사양을 고정 사용한다.
현실 특정 제품의 훈련기를 복제할 필요는 없지만, 게임 내 눈금은 일관되고 판독 가능해야 한다.

반드시 다음을 만족한다.
60.1 본척이 있다.
60.2 부척이 있다.
60.3 측정값에 따라 부척 위치가 달라진다.
60.4 특정 부척 눈금이 본척 눈금과 정렬된다.
60.5 플레이어가 눈으로 값을 추론할 수 있다.
60.6 정답 숫자를 옆에 표시하지 않는다.

============================================================
60.7 버니어 표시값 계산 흐름
============================================================

권장 구조:
MeasurementService
→ GetTrueDimension()
→ MeasurementInstrumentModel
→ GetInstrumentReading()
→ VernierDisplayModel
→ VernierRenderer

VernierDisplayModel 예:
- MainScaleBase
- SliderPosition
- VernierOffset
- AlignedVernierIndex
- JawOpening

화면에서는 이 DisplayModel을 사용한다.
UI가 직접 TrueDimension을 읽어 텍스트로 출력하지 않는다.

============================================================
60.8 MeasurementPage UI 구성
============================================================

상단:
- 제목: "측정"
- 대상: "마모된 펌프 축"

측정 위치 패널:
[L1 직경]
[L1 길이]
[L2 직경]
[L2 길이]
[L3 직경]
[L3 길이]

중앙:
- 확대된 VernierView
- 본척
- 부척
- 죠
- 선택한 측정 위치 강조

하단:
읽은 값 입력
[              ] mm

[기록]
[다시 측정]
[기록 목록]
[돌아가기]

가공 중이라면:
[가공으로 돌아가기]

중요:
입력칸은 항상 플레이어가 직접 입력한다.
MeasurementPoint를 선택했다고 자동으로 채워지면 실패다.

============================================================
60.9 측정 화면의 UI 우선순위
============================================================

MeasurementPage에서 가장 중요한 것은 버니어다.

우선순위:
60.1 버니어 눈금
60.2 측정 대상 위치
60.3 입력칸

절대 금지:
- 거대한 퀘스트창이 버니어를 가림
- 버니어 위에 튜토리얼 창 표시
- 숫자 정답 텍스트를 눈금 옆에 표시
- 입력칸에 자동 정답 입력
- 일반 HUD가 눈금 영역 침범

============================================================
60.10 측정 모드 진입 조건
============================================================

선반에서 측정하려면:
- Workpiece가 존재
- 측정 가능한 MeasurementPoint 존재
- 버니어 보유
- Quest/게임 상태가 측정 허용
- 주축 정지

주축이 회전 중이면 측정 모드 진입 금지.

한국어 안내 예:
"주축이 회전 중입니다."
"측정하려면 먼저 주축을 정지하세요."

60.11 고장 펌프 축 측정
============================================================

정상 원래 형상:
전체 길이 100 mm
L1 = Ø40 × 30
L2 = Ø50 × 40
L3 = Ø40 × 30

고장품:
- L1 정상에 가까움
- L2 정상에 가까움
- L3 직경 마모
- L3 길이 방향 마모

플레이어가 L3를 재면 "원래 Ø40 × 30"을 보여주면 안 된다.
버니어는 오직 현재 마모되어 남아 있는 실제 치수만 표현한다.

60.12 첫 퀘스트에서 플레이어가 배우는 사고 과정
============================================================

목표:
"측정값 = 설계값"이 항상 성립하지 않는다는 것을 직접 이해하게 한다.

진행:
60.1 L1 측정
60.2 L2 측정
60.3 L3 측정
60.4 L3가 반대쪽과 다름을 확인
60.5 시각적 마모 흔적 확인
60.6 전체 형상 대칭성 관찰
60.7 L1이 L3의 원래 대응 형상일 가능성 판단
60.8 전체 길이 정보 및 형상을 함께 판단
60.9 원래 L3 형상을 추론

버니어:
"지금 이 부품이 현재 어떻게 되어 있는지"

WorkMemo/관찰:
"이 부분은 마모된 것 같다"

"그러면 원래 형상은 반대편과 같았을 가능성이 높다"

이것이 핵심 게임플레이다.

60.13 WorkMemo와 측정 연동
============================================================

WorkMemo는 정답 공개창이 아니다.

처음:
펌프 축
도면 없음

L1 측정 후:
플레이어가 기록한 값만 표시 가능.

예:
L1 직경
기록: 40.0

이 값은 RecordedMeasurement이다.
실제 내부 치수와 자동 동기화하지 않는다.

L3 측정 후:
관찰:
- 마모 흔적 있음
- 반대쪽과 형상이 다름

추론 완료 전에는:
"원래 L3 = Ø40 × 30"
자동 표시 금지.

ShapeInferred 이후에만:
추정 원형
L1 Ø40 × 30
L2 Ø50 × 40
L3 Ø40 × 30
전체 100

을 표시할 수 있다.

60.16 최종 검사
============================================================

가공 완료 후 필요한 MeasurementPoint를 다시 측정한다.
플레이어가 값을 직접 기록한다.

PartEvaluator는 RecordedMeasurement가 아니라 실제 Workpiece Geometry를 기준으로 기능 판정한다.

예:

PartEvaluator는 Ø38.50을 평가한다.
RecordedMeasurement는 "플레이어가 무엇이라고 판단했는가"를 나타낼 뿐이다.

============================================================

[기록]

60.18 첫 버니어 획득 튜토리얼

"에헤이~."
"그건 네 삼촌이 그런 데 쓰라고 남긴 게 아닐 텐데."

시스템:

박성철:
"여기가 본척이고, 이쪽 움직이는 게 부척이야."

60.19 측정 위치 시각화
============================================================

MeasurementPoint 선택 시 플레이어가 어디를 재고 있는지 명확해야 한다.

L1 직경:
- L1 구간 강조
- 버니어 죠가 해당 외경을 잡는 그림
- 나머지 구간 약간 어둡게

L2 길이:
- L2 양 끝 기준선 표시
- 현재 선택 구간 강조

플레이어가 "이 치수가 어느 부분인지" 헷갈리지 않게 한다.

- Length

둘을 하나의 의미 없는 공통 버튼으로 뭉개지 않는다.

- 주요 외경/길이 측정

- 직접 기록

금속 자가 버니어와 같은 정밀 측정 기능을 제공하면 안 된다.

61. 화면 연출 / 환경 / 씬 구성 상세 구현 명세 — 통합본
============================================================

[권위 규칙]
이 Section은 화면 배치, 대화 UI, Quest UI, Workshop/Farm/Pump 환경,
씬 구성, Presentation 품질 판정에서 가장 높은 우선순위를 가진다.
기능이 존재한다는 이유만으로 시각적 구현을 완료 처리하지 않는다.

61.0 핵심 목적
이 문서는 '기능은 있으나 화면이 허접한 프로토타입'을 방지한다. Codex는 기능 존재만으로 완료 처리하지 않는다. 플레이어가 무엇을 보고, 어디를 바라보고, 무엇을 조작하는지 명확해야 한다.

절대 원칙:
- 스토리 화면에서는 장소와 인물이 주인공이다.
- 가공 화면에서는 기계·공작물·공구가 주인공이다.
- 측정 화면에서는 측정기와 눈금이 주인공이다.
- UI는 주인공을 가리지 않는다.
- 모든 Player-facing 텍스트는 한국어다.
- Placeholder는 개발 중 허용하지만 빈 회색 방/Cube 몇 개를 Presentation 완료로 취급하지 않는다.

61.1 DialoguePage
대화창은 화면 하단 약 30~35% 높이에 고정한다. 상단 65~70%는 현재 Scene과 NPC가 계속 보이는 영역으로 남긴다.

구성:
- 화자 이름
- 대사 본문
- 다음 진행 표시
- 선택지 연결 영역
- 필요 시 NPC 초상/반신 영역

개념:
┌──────────────────────────────────────────────┐
│                                              │
│            현재 Scene / 현재 NPC             │
│                                              │
│                                              │
├──────────────────────────────────────────────┤
│ 박성철                                       │
│ "에헤이~. 첫날부터 일이 생겼구먼."           │
│ "같이 가보지."                     [다음 ▶] │
└──────────────────────────────────────────────┘

금지:
- 화면 중앙 기본 팝업으로 대사 표시
- 전체 화면 불투명 대화창
- 상단 Toast 형태 대사
- 화자 이름 없이 본문만 표시
- 영어 placeholder
- 배경/인물을 완전히 가림

대화 중 Gameplay/기계 입력을 잠그고 DialogueContext를 사용한다. 종료 후 이전 Context로 복귀한다.

61.2 ChoicePanel
DialoguePage와 시각적으로 연결한다. 선택지는 대화창 바로 위 또는 내부 상단에 표시하며 Scene 대부분을 가리는 별도 거대 Modal로 만들지 않는다.

예:
[기본 정도는 알고 있습니다.]
[오래돼서 좀 가물가물합니다.]
[잘 모릅니다.]

61.3 Quest UI는 반드시 3종으로 분리
A. QuestPopup: 시작/중요 갱신/완료 순간에만 일시 표시.
B. QuestTracker: 일반 플레이 중 모서리에 2~3줄로 작게 표시.
C. QuestLogPage: 플레이어가 직접 열 때만 상세 정보 표시.

가공 중 Tracker 예:
멈춰버린 펌프
새 펌프 축을 가공하자

절대 금지:
- 가공 화면의 1/3 이상을 Quest Window가 상시 차지
- Workpiece/Tool/Vernier를 Quest UI가 가림
- 긴 Quest 설명 상시 노출

61.4 공통 화면 Safe Area
Primary View Area 중앙에는 세계/NPC/공작물/측정기가 보여야 한다. Quest, Tutorial, Inventory, Debug Panel은 상시 중앙을 가리지 않는다. 큰 Modal은 플레이어가 직접 열었을 때만 허용한다.

61.6 가공 카메라 — Projection Requirements 포함
자유 카메라가 아니라 고정 Orthographic View 4개:
- 정면 Front
- 평면 Top
- 우측면 Right
- 등각투영 Isometric

절대 규칙:
- 네 View 모두 Unity Camera Projection 자체가 Orthographic이어야 한다.
- Perspective Camera의 각도만 바꾸어 정면/평면/우측면으로 보이게 하는 구현은 FAIL이다.
- Isometric View 역시 Perspective가 아니라 Orthographic Projection의 등각 방향 카메라다.
- 원근감 때문에 동일한 형상이 깊이에 따라 작아지거나 커져 보이면 안 된다.
- View 전환 시 Orthographic Size는 공작물/공구가 읽히도록 각 View별 설정값을 사용할 수 있다.

Turning 기본 = 정면.
키보드 단축키와 화면 UI 버튼 모두 제공. View 전환 시 UI 위치는 유지. 마우스 휠 Zoom 금지. 향후 Milling도 같은 CameraView 시스템을 공유한다.

61.7 MeasurementPage
Section 60 측정 시스템 상세 구현 명세를 최우선 적용한다.

시각 우선순위:
1) 확대된 버니어
2) 본척/부척 눈금
3) 측정 위치/대상
4) 직접 입력칸
5) 기록 버튼
6) Quest 정보

Quest UI가 눈금을 가리면 FAIL. 실제 치수 숫자 자동 표시는 절대 금지.

61.8 Workshop Scene — '빈 방 + 선반' 금지
Workshop은 김영호가 실제로 오래 사용했던 낡은 소형 가공 작업장으로 보여야 한다.

필수 Landmark:
- 범용선반: 가장 중요한 Landmark
- 작업대: 고장품 분석/측정과 연결
- 공구 보관 구역: 바이트/교환공구/공구함
- 소재 보관 구역: 탄소강 원형봉이 보관되어 있다는 시각적 정보
- 김영호 기록 공간: 노트, 책장, 종이, 작업 흔적
- 향후 설비가 들어올 빈 공간

권장 Props:
공구함, 렌치류 실루엣, 금속 봉재, 작업등, 낡은 의자, 선반/책장, 케이블, 배전함, 금속 상자, 용기, 작업 노트, 벽 표식, 금속 부품, 바닥 마모/얼룩, 오래된 조명.

모든 Props가 상호작용 가능할 필요는 없다. 목적은 '사람이 일했던 공간'이라는 정보량이다.

재질/조명:
- 바닥/벽/기계/작업대/금속 소품이 서로 구분돼야 함
- 모든 오브젝트 동일 기본 회색 Material 금지
- 낡음/금속/콘크리트/먼지/부분적 녹/사용감
- 핵심 상호작용 위치는 조명으로 읽혀야 함
- 균일한 기본 Ambient만으로 끝내지 않음

61.9 Farm Scene — '초록 바닥 + 펌프' 금지
즉시 농업 시설임을 알 수 있어야 한다.

필수:
- 작물 구역 또는 비닐하우스 맥락
- 물 배관
- 펌프 설비
- 수조/물탱크 또는 공급원 맥락
- 호스/배수로
- 농작업 소품
- 이서연이 여기서 일한다는 생활 흔적

권장 동선:
Scene Entry → 농업 공간 → 이서연/박성철 → Pump Landmark → 조사.
펌프를 구석에 작게 묻지 않는다.

복구 전:
- 펌프 정지
- 물 없음
- 작동음 없음
- 물 공급 중단 느낌

복구 후:
- 펌프 작동
- 물 흐름
- 물 소리
- 배관/호스/수로 변화
- 이서연 반응

61.10 Pump = QUEST 01 Hero Prop
단순 Cube/Cylinder 몇 개를 최종 펌프로 취급하지 않는다.

전문 지식이 없는 플레이어도 '물을 보내는 오래된 동력 기계'라고 이해할 수 있어야 한다.

필수 시각 요소:
- Motor Section
- Pump Body
- Shaft/Coupling Area
- Inlet Pipe
- Outlet Pipe
- Base/Frame
- 고정 요소
- 물 공급 방향을 이해할 수 있는 연결 구조

권장:
보호 커버, 라벨/표식, 플랜지/볼트 느낌, 배관 이음부, 녹/도장 벗겨짐, 유지보수 흔적.

멀리서도 '모터 + 펌프 + 배관' 실루엣이 읽혀야 한다.

고장 상태:
- 회전 없음
- 물 없음
- 소리 없음
- 축/커플링 영역을 조사 대상으로 읽을 수 있음
- 스토리상 박성철이 커버를 열거나 일부를 분해하는 단순 연출 가능

복구 상태:
- 회전 표현
- 약한 진동
- 작동음
- 물 흐름
- 배관/호스/수로 효과

Quest Complete 글자만 뜨고 펌프가 그대로면 FAIL.

61.11 NPC 배치
Workshop의 박성철은 선반/작업대 근처. Farm의 이서연은 농업 공간/펌프와 연결된 위치. Pump 조사 시 박성철은 펌프 가까이 이동해 조사 대상을 바라본다.

대화 시 현재 화자가 화면에 보이거나 카메라/시선으로 누구인지 자연스럽게 읽혀야 한다. NPC가 화면 밖인데 대사만 뜨는 상황을 피한다.

61.12 NPC Placeholder 최소 품질
박성철과 이서연은 최소한 실루엣/복장 맥락/초상 등으로 서로 구분 가능해야 한다. 모든 NPC를 동일 Capsule + 이름표만 바꾼 상태로 Presentation 완료 처리하지 않는다.

61.13 Scene Entrance / Establishing
Workshop 최초 진입: 선반, 작업대, 낡은 작업장이라는 장소성이 읽히는 구도.
Farm 최초 진입: 농업 공간, 물 관련 설비, NPC가 읽히는 구도.

짧은 Location Title 허용:
DAY 1
삼촌의 작업장

또는
농장

오래 화면을 가리지 않는다.

61.14 DAY 1 Presentation Flow
14.1 Fade from black → LAST MACHINIST → DAY 1 / 삼촌의 작업장 → Workshop 노출.

14.3 이서연 등장: 입구 방향에서 등장하거나 등장 사실이 시각적으로 명확해야 함.
"성철 아저씨! 잠깐만 와봐요. 기계가 또 안 돌아가요!"
박성철: "에헤이~. 첫날부터 일이 생겼구먼." / "같이 가보지."

14.6 Workshop 복귀: 작업대에서 고장 축 조사 → 금속 자 → 박성철 '……뭘로 쟀나?' / '…….' / '에헤이~.' → 낡은 버니어 획득 → MeasurementPage 연결.

61.16 Inventory
플레이어가 직접 열 때만 큰 Page. 상시 표시 금지.
고장 축 상세 예:
마모된 펌프 축
도면 없음.
한쪽 끝에 심한 마모 흔적이 있다.
중앙이 더 굵은 3단 축 형태로 보인다.
측정/추론 전 정답 치수 금지.

61.17 WorkMemo
Debug Table이 아니라 작업 기록장 느낌. 대상/관찰/플레이어 측정 기록/확보 단서/추론 결과를 표시. 정보는 진행에 따라 점진 해금. 측정하지 않은 값을 자동 채우지 않는다.

61.18 Tutorial
큰 강의창 금지. 필요한 순간 기능 하나만 짧게. 핵심 오브젝트를 가리지 않는다.
선반 예: X/Z 축 선택, 1/2/3 배율, 마우스 휠 핸들.
버니어 첫 1회: [본척], [부척] 라벨/강조 허용. 정답 숫자 공개 금지.

61.19 Toast
작고 일시적. 예:

여러 Toast가 무한히 쌓이지 않는다.

61.20 화면 정보 밀도
밋밋함은 HUD를 늘려 해결하지 않는다. 환경 정보량을 늘린다.
좋음: 배관, 공구, 작업 흔적, 소재, 구조물, 조명, 표면 차이, 사용감.
나쁨: Quest 텍스트 8줄, HUD 숫자 15개, 거대 Tutorial, Debug 값, 불필요한 버튼.

61.21 UI Layer
Layer 0 World: Environment/Machine/Workpiece/NPC

Layer 2 Small Tracker: QuestTracker

61.22 Modal
Modal이 열리면 뒤 Gameplay 입력 잠금, 중복 입력 방지, 명확한 닫기/돌아가기, 종료 후 이전 Context 복귀. QuestTracker는 Modal 아님.

61.23 한국어/Typography
한글 Glyph 지원 Font Asset 사용. 이름/대사/버튼 줄바꿈 확인. 영어 기준 좁은 버튼 금지. '가공으로 돌아가기' 같은 문자열이 버튼 밖으로 삐져나오면 FAIL.

61.24 Audio

64. v0.5 UPDATE — EXTERNAL IMAGE ASSET / NPC ILLUSTRATION POLICY
============================================================

본 섹션은 v0.5에서 새로 추가된 규칙이다. 기존 v0.4와 충돌할 경우 본 섹션을 우선한다.

Last Machinist의 NPC 최종 표현은 외부에서 제공되는 이미지 에셋 또는 별도로 제작된 일러스트 에셋을 우선 사용한다. Codex의 역할은 이미지 제작이 아니라 Import, Sprite 설정, UI 연결, NPC별 Asset Binding, 표정 Variant 교체, DialoguePage 배치, Resolution/Scaling 확인, Scene 연결, Missing Reference 방지다.

금지:
- NPC 최종 외형을 Capsule/Cube/기본 3D Model로 확정
- 임시 Placeholder를 최종 Character Asset으로 취급
- 제공된 NPC Illustration을 무시하고 자체 3D 캐릭터 사용
- 제공된 Aspect Ratio를 찌그러뜨림
- 낮은 해상도 Placeholder를 최종 Asset으로 유지

개발 중 Placeholder는 허용하지만 최종 Presentation 기준에서는 Character Illustration/Sprite로 교체되어야 한다.

============================================================
74. ORTHOGRAPHIC PROJECTION — ABSOLUTE REQUIREMENT
============================================================

가공 화면의 4개 Camera View는 단순히 Perspective Camera의 위치와 각도만 바꾼 것이 아니다. Camera Projection 자체가 반드시 Orthographic이어야 한다.

필수:
Camera.orthographic = true 또는 동등한 Orthographic Projection 설정

4 View:
- Front / 정면
- Top / 평면
- Right / 우측면
- Isometric / 등각투영

모든 View는 Orthographic Projection을 사용한다.

Orthographic의 의미:
- 원근 축소가 없어야 함
- 동일 크기의 형상은 화면 깊이에 따라 임의로 작아지지 않음
- 형상 비교가 Perspective 왜곡에 영향을 받지 않음

Isometric도 Perspective Camera를 비스듬히 둔 것이 아니라 Orthographic Camera를 등각 방향으로 배치한다.

FAIL:
- Perspective 상태에서 Front 각도만 변경
- Perspective 상태에서 Top View 흉내
- Perspective 상태의 Isometric-like View
- FOV 조절로 Orthographic처럼 보이게 함

PASS:

78. v0.6 TITLE / DAY / QUEST DISPLAY POLICY
============================================================

게임의 제목, DAY/Chapter 표시, Quest 제목은 서로 다른 정보 계층이다.

이 세 종류의 텍스트를 하나의 타이틀 카드처럼 합쳐 표시하지 않는다.

------------------------------------------------------------
78.1 GAME TITLE
------------------------------------------------------------

게임 시작 직후 표시 가능한 게임 제목:

LAST MACHINIST

이 시점에는 Quest 제목을 표시하지 않는다.

금지 예:

LAST MACHINIST
멈춰버린 펌프

LAST MACHINIST
QUEST 01
멈춰버린 펌프

게임 제목 아래에 현재 Quest 제목을 자동으로 붙이지 않는다.

------------------------------------------------------------
78.2 DAY / LOCATION TITLE
------------------------------------------------------------

게임 제목 이후 별도의 화면 또는 짧은 타이틀 연출로 표시한다.

예:

DAY 1
삼촌의 작업장

권장 순서:

검은 화면
↓
LAST MACHINIST
↓
Fade
↓
DAY 1
삼촌의 작업장
↓
Workshop Scene 시작

DAY/Location Title은 Quest Title이 아니다.

금지:

DAY 1
멈춰버린 펌프

처럼 DAY와 Quest를 하나의 챕터 제목처럼 합쳐 표시하는 것.

------------------------------------------------------------
78.3 QUEST TITLE
------------------------------------------------------------

Quest 제목은 해당 Quest가 실제로 발생하거나
플레이어가 수락/활성화한 뒤에만 표시한다.

첫 Quest의 경우:

이서연 등장
↓
펌프 문제 설명
↓
Quest 활성화
↓
QuestPopup 표시

표시 예:

의뢰 시작
「멈춰버린 펌프」

QuestPopup은 일시적이다.
그 이후에는 작은 QuestTracker만 남는다.

------------------------------------------------------------
78.4 QUEST TITLE PREMATURE REVEAL 금지
------------------------------------------------------------

첫 게임 시작 직후에는
"멈춰버린 펌프"를 보여주지 않는다.

플레이어가 아직 이서연을 만나지 않았고
펌프 문제를 알지 못하는 시점에는 Quest 정보를 공개하지 않는다.

이는 UI 정리뿐 아니라 스토리 순서 보존 규칙이다.

============================================================

권장:

CharacterDefinition
ScriptableObject
또는 동등한 Asset Binding Data

예:

CharacterId = character_seongcheol
DisplayName = 박성철
DialogueDefault = NPC_Seongcheol_Dialogue_Default
WorldDefault = NPC_Seongcheol_World_Default

Quest/Dialogue Script는:

"박성철이면 이 PNG를 로드"

식으로 직접 처리하지 않는다.

Dialogue Logic:
CharacterId
+
ExpressionId

만 전달한다.

Asset Resolver가 실제 Sprite를 연결한다.

------------------------------------------------------------
85.1 MISSING ASSET
------------------------------------------------------------

필요한 Asset이 없으면 Codex는:

1. Missing 여부를 보고한다.
2. Placeholder Slot을 사용한다.
3. 예상 파일명을 알려준다.
4. 임의의 저품질 최종 이미지를 만들어 완료 처리하지 않는다.

예:

Missing:
NPC_Seoyeon_Dialogue_Worried.png

Fallback:
NPC_Seoyeon_Dialogue_Default.png

이 경우 Console/Error Popup을 플레이어에게 보여줄 필요는 없다.
개발자 로그로 남길 수 있다.

89. v0.7 LATHE HANDWHEEL / DIAL UI REDEFINITION
============================================================

현재 구현에서 "다이얼"이라고 적힌 단순 버튼은
최종 Lathe Control로 인정하지 않는다.

원형 Handwheel / Dial UI로 표현한다.

필수:
- X Handwheel과 Z Handwheel은 서로 독립
- 원형 조작기처럼 보여야 함
- 마우스 드래그 또는 회전 제스처로 조작 가능
- 마우스 휠 입력과 동일 Command Layer 사용

금지:

- [Z 다이얼] 텍스트 버튼
- 단순 + / - 버튼만 제공

90. v0.7 QUEST UI LAYER / VISIBILITY RULE
============================================================

Quest UI가 다른 UI 뒤에서 애매하게 반쯤 가려진 상태로 남는 것을 금지한다.

Quest UI는 계속 다음 세 역할로 분리한다:
1. QuestPopup
2. QuestTracker
3. QuestLogPage

Modal UI가 열릴 때 QuestTracker는 다음 중 하나로 처리:
A. 완전히 숨김
B. 명확히 Dim 처리
C. Modal 밖의 안전한 영역으로 재배치

절대 금지:
- 다른 Panel 뒤에서 글자 일부만 보임

- Modal과 겹쳐 내용이 반쯤 잘림
- Lathe/Measurement UI 위에 Quest Panel이 겹침

Modal이 열리면 하위 UI의 Visibility 상태를 명시적으로 제어한다.

91. v0.7 MACHINING ↔ MEASUREMENT LOOP — ABSOLUTE REQUIREMENT
============================================================

가공 중 반복 측정은 Last Machinist의 핵심 플레이 루프다.

"가공이 끝난 뒤 최종 검사에서만 측정" 구조는 금지한다.

반드시 다음 흐름을 지원한다.

가공
→ 주축 정지
→ 측정
→ 버니어 직접 판독
→ 값 기록
→ 같은 공작물 상태로 가공 복귀
→ 추가 가공
→ 재측정

측정 전후에 Workpiece Geometry가 유지되어야 한다.

측정 화면 진입/복귀 때문에 다음이 초기화되면 FAIL:
- Workpiece Geometry
- Tool Position
- Reclamp State
- ProcessHistory

Machining 상태에서도 조건 만족 시 MeasurementPage 진입 가능:
- Workpiece Mounted
- 주축 정지
- 측정기 보유
- 측정 가능한 MeasurementPoint 존재

동일 MeasurementPoint 반복 측정 가능.

예:
L1 직경 1차 기록 41.2
→ 추가 가공
→ 2차 기록 40.4
→ 추가 가공
→ 3차 기록 40.1

측정 후 게임이 "0.2 mm 더 깎으세요"처럼 직접 정답을 알려주면 안 된다.

97. v0.8 LATHE HANDWHEEL — IMAGE ASSET BASED FINAL VISUAL RULE
============================================================

v0.7에서 정의한 "실제 회전 가능한 X/Z Handwheel" 기능은 유지한다.

단, 최종 Handwheel 외형은
Unity 기본 도형, 단순 Vector Graphic, Primitive 원형 UI를
코드로 조합한 모습으로 완료 처리하지 않는다.

최종 시각 표현은 외부 PNG 이미지 Asset을 기반으로 한다.

핵심 분리:

IMAGE ASSET
→ Handwheel의 외형 담당

CODE
→ 회전 입력
→ 회전 Animation
→ Axis 이동량 계산
→ Command 전달

즉:

"이미지처럼 보이는 버튼"
이 아니라

"이미지 Asset으로 만든 실제 회전 조작기"

여야 한다.

------------------------------------------------------------
97.1 HANDWHEEL VISUAL COMPONENTS
------------------------------------------------------------

권장 구성:

A. Handwheel Wheel
- 실제 회전하는 원형 휠 본체

B. Handle / Grip
- 휠 가장자리에 붙은 손잡이
- Wheel과 함께 회전하거나 별도 Child로 연결

C. Fixed Base / Mount
- 기계에 고정된 베이스
- 회전하지 않음

D. Optional Scale / Dial Plate
- 필요할 경우 고정 또는 별도 회전
- MVP에서 과도하게 복잡한 실제 눈금 구현은 필수 아님

E. Axis Label
- X 또는 Z
- 이미지에 직접 구워 넣기보다 UI Text로 분리 권장

------------------------------------------------------------
97.2 ASSET DIRECTION MUST MATCH
------------------------------------------------------------

선반 Handwheel에 쓰이는 모든 이미지 Asset은
같은 카메라 방향과 같은 시점으로 통일한다.

기본 방향:

정면(Front-facing)

필수:
- Wheel을 정면에서 봄
- Handle도 정면 기준
- Base도 정면 기준
- X/Z에서 동일한 시각 방향 사용
- 서로 다른 Perspective 각도를 섞지 않음

금지:
- Wheel은 정면인데 Handle은 측면
- Base는 사선 Perspective
- X Handwheel과 Z Handwheel의 시점이 서로 다름
- 이미지마다 광원 방향이 심하게 달라 조립했을 때 따로 노는 느낌

목표:
부품을 겹쳤을 때 하나의 기계 조작부처럼 보여야 한다.

------------------------------------------------------------
97.3 TRANSPARENT IMAGE ASSET
------------------------------------------------------------

Handwheel 구성 부품은 기본적으로:

PNG
Transparent Background

사용을 권장한다.

예:

UI_Lathe_Handwheel_Wheel.png
UI_Lathe_Handwheel_Handle.png
UI_Lathe_Handwheel_Base.png

필요하면:

UI_Lathe_Handwheel_Scale.png
UI_Lathe_Handwheel_CenterCap.png

외부 에셋 위치:

Assets/_Project/Art/External/UI/Lathe/Handwheel/

------------------------------------------------------------
97.4 X / Z HANDWHEEL ASSET REUSE
------------------------------------------------------------

X와 Z Handwheel의 디자인이 같다면
동일 이미지 Asset을 재사용할 수 있다.

예:

UI_Lathe_Handwheel_Wheel.png

을 X/Z 양쪽에서 공통 사용하고

X / Z 표시는 별도 UI Text 또는 Label로 구분한다.

불필요하게 동일 이미지를
_X / _Z로 복제하지 않는다.

단,
실제 화면상 크기나 배치가 다르면
Prefab 설정만 별도로 둘 수 있다.

------------------------------------------------------------
97.5 PIVOT / ROTATION
------------------------------------------------------------

Wheel Image의 Pivot은
실제 회전 중심과 일치해야 한다.

권장:

Pivot = Center

Handle이 Wheel의 Child일 경우:
Wheel Parent가 회전하면 Handle도 함께 회전한다.

구조 예:

LatheHandwheel_X
├─ BaseImage        (Fixed)
├─ RotatingGroup
│  ├─ WheelImage
│  └─ HandleImage
└─ AxisLabel        (Fixed)

RotatingGroup만 회전한다.

Z축도 동일 구조를 사용한다.

------------------------------------------------------------
97.6 HANDWHEEL INPUT
------------------------------------------------------------

기능은 v0.7 규칙을 유지한다.

허용:
- Mouse Drag
- Circular Drag
- Mouse Wheel
- Keyboard
- 미래 Touch

모든 입력은:

LatheInputRouter
→ ApplyHandwheelDelta(Axis, delta)

동일 Command Layer를 사용한다.

이미지 에셋으로 교체했다고
기존 회전 기능이 사라지면 FAIL.

QuestTracker != Quest Checklist

Hint는 기본적으로 숨겨도 된다.

Hint 표시 조건 예:
- 플레이어가 Hint 버튼 선택
- 특정 Tutorial 구간
- 플레이어가 장시간 진행하지 못함
- Quest Design에서 명시적으로 허용된 경우

첫 Quest 측정 Hint 예:

"마모된 부분의 현재 치수가 원래 형상과 같다고 단정할 수는 없다."

금지:
- Hint가 정답 치수를 공개
- Hint가 항상 Tracker 아래 여러 줄로 표시
- "Ø40으로 만들어라" 식으로 추론을 대신함
- 가공 중 "0.2 mm 더 깎아라" 식 직접 지시

102. QUESTTRACKER SIZE / LAYER RECONFIRMATION
============================================================

v0.7 Quest UI Layer 규칙을 유지한다.

QuestTracker는:
- 작은 HUD
- 현재 목표 1~2줄
- 화면 모서리
- 핵심 Gameplay 영역 비침범

LathePage:
QuestTracker는 매우 작게 유지.

MeasurementPage:
버니어 판독을 방해하지 않음.

Modal Page:
QuestTracker는 숨김 / Dim / 안전영역 이동 중 하나.

Current Objective 기능이 추가되었다고
QuestTracker 크기를 다시 키우지 않는다.
